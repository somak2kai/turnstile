One noisy customer, one AI model: round robin

35 customers share one AI model (Claude Haiku). One customer, pebbleapp, floods it. pebbleapp asked for about 9,700 requests a second, while Haiku can handle about 3,000 a second for all customers combined. About half of all traffic in the test goes to this model from that one customer. Press play and watch what Turnstile does with everyone else's requests. This replay uses the round-robin policy: customers with waiting requests take turns, one request each.

What this shows

  • The flood stays with the flooder. Everyone else's requests are answered as fast as the model can work, and none of them time out. Only pebbleapp's own line gets long.
  • pebbleapp gets the leftovers. Whatever capacity the other customers don't need goes to pebbleapp. But pebbleapp sends far more than the model can handle, so most of its requests have waited so long in its line that they run out of time before an answer comes back.
  • The budget is a rolling 60 seconds. The meter fills for the first minute, then levels off as old usage drops out while new usage comes in.
  • Round robin and least served look the same here. Compare with the least-served replay: both give identical results in this test, because the other customers never have to wait. The policies only differ when several heavy customers compete for the same model.

Replay of 150 seconds of Turnstile's benchmark (Apple M1 Pro, 640 simulated clients). The test uses a fake AI model that answers in 1–10 ms instead of the real 0.5–5 s, so it is about 500× faster than real life, and the token limit is scaled up by the same amount. Requests give up after 60 ms of test time (30 s in real terms). Counts are per second of test time.
